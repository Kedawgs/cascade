# Cascade v3.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement Cascade v3.2 as specified (six contracts, four fixed linked libraries and two read-only lenses in the approved one-vault code layout of §8.1, rebuilt around a stake ledger, a parking Bittensor adapter, bounded tolerances, one owner scheduler with hard bounds and an owner-signed stamp, and two-door exit limits), teach ops, the keeper, the monitor and the web to run it, rehearse it on forks and on testnet, deploy it by path A and retire v3-launch.

**Architecture:** Contracts first, in the spec's order: the compiler switch and a size gate, the pure payout library; then the one-vault layout of §8.1 laid down before the vault grows (a shared layout file, file-level events and errors and the published vault ABI; a minimal share token; `extsload` with two lenses over generated layout constants; and the three storage-writing libraries moved out of today's code without a behaviour change: L1 the batch path, L2 the unstake walk, L3 the payout engine), so that every later feature is written into the library or lens that owns its subsystem and every size gate stays green; then the scheduler and exits machine in `CascadeBase`, the vault, the adapters, the front door and oracle, the staker; then the invariant campaign and the named exits-machine tests; then the off-chain stack (ops deploy, verify, stamp and sign page; keeper jobs; monitor rules; web copy); then fork and testnet rehearsals whose measurements feed three constants; then the deploy and v3-launch's retirement. Every contract task is test-first, and every v3.1 PoC is ported in Task 1 and inverted by the task that fixes it.

**Tech Stack:** Solidity 0.8.38 (`via_ir`, `evm_version = cancun`), Foundry 1.7 (`~/.foundry/bin`), OpenZeppelin 5.4.0; ops: Node 24, TypeScript 5.9, viem 2.57.7, vitest; indexer: Cloudflare Worker, vitest; web: Next.js 16, wagmi 3, viem, vitest.

**Spec:** `docs/superpowers/specs/2026-10-31-cascade-v3.2-design.md` (revision 13: revision 10's design with the founder decisions of 2026-10-31, and the one-vault code layout of revisions 11 to 13, §8 and §8.1). The per-task rulings are in `.superpowers/sdd/2026-11-01-cascade-v3.2-implementation/rulings-index.md`; a task marked "dispatched as Na and Nb" is split there. "§3.6" is a section of the spec, "I-n" an invariant, "T-<row>.<col>" a scenario test of §3.6's table, listed in §9.1. Read the spec's section before each task; the plan records only what the spec leaves to the implementer.

## Review Focus

1. **A stale "Send it now".** A user sends `closeBatch(id, minValue)` just after the batch left or after a cancel lowered its value: the contract reverts `WrongBatch(id)` or `BatchTooSmall()`, and the web must say what happened in plain words (the deposit is already on its way, or the batch changed), never show a raw revert or retry another batch. Test: Task 58 `sendNowRevertCopy`.
2. **A signature in an unexpected shape, or a stamp dated by the wrong clock.** A Ledger through MetaMask can return `v` as 0 or 1, and some wallets a 64-byte compact signature; the contract takes only 65 bytes with `v ∈ {27, 28}`. And a stamp dated by the wall clock while Bittensor's head lags it reverts `StampOutOfWindow`. `pnpm ops stamp` must normalise or refuse before relaying, and date `asOf` from each chain's head. Tests: Task 48.
3. **A cancel whose cursor sits inside the bounces.** The owner cancels a batch part-paid inside its bounce prefix; the keeper must rebuild the carried list as the last `bouncesCarried` bounce entries and pay it, and must treat a later `NothingToCancel` as final, not retry. Tests: Task 22 (vault), Task 50 (keeper).
4. **A Base address whose origin is elsewhere.** A holder whose origin is `DIRECT_ORIGIN` or another chain requests a redeem on Base: the vault skips it (`RedeemSkipped`) and the request fee is spent for nothing. The web must warn before the request when it can read the origin, and explain after (set the origin from Bittensor, or redeem directly). Tests: Task 18 (vault), Task 59 (web).
5. **A deployer key that is not fresh.** A deployer whose nonce is not the plan's, or with a pending transaction at the planned nonce, shifts every predicted address baked into the other chain's immutables. `pnpm ops deploy` must refuse before the first `CREATE`, and any revert must end the run (fresh keys, new plan). Tests: Task 44.

## Phase 2: The payout library and the one-vault layout

### Task 5: `CascadePayoutMath`, then size gate A

**Files:**
- Create: `contracts/src/libraries/CascadePayoutMath.sol`; Modify: `contracts/src/CascadeVault.sol` (`_verifyPayouts`, `_takeChunk`, `_deductFee` delegate to it; `PayoutsMismatch` moves to the library); `contracts/README.md` (Slither verdict)
- Test: `contracts/test/libraries/CascadePayoutMath.t.sol`

**Interfaces:**
- Produces (external, `pure`, linked; the vault passes what it reads from storage and emits every event):
  ```solidity
  library CascadePayoutMath {
      error PayoutsMismatch();
      error FeeTooHigh();
      function hashStep(bytes32 h, address user, uint256 shares, uint256 assets) internal pure returns (bytes32); // keccak256(abi.encode(h, user, shares, assets))
      function verify(CascadeMessages.Payout[] calldata payouts, uint256 count, bytes32 payoutsHash) external pure;
      function takeChunk(CascadeMessages.Payout[] calldata payouts, uint256 start, uint256 limit, uint256 cap, uint256 minChunk)
          external pure returns (CascadeMessages.Entry[] memory entries, uint256 sum);
      function deductFee(CascadeMessages.Payout[] calldata payouts, uint256 start, uint256 taken, uint256 charged, uint256 sum)
          external pure returns (CascadeMessages.Entry[] memory kept, CascadeMessages.Entry[] memory dust, uint256 net);
  }
  ```

## Notes the spec left open, decided here

**2026-11-01, Phase 3 and Checkpoint R1 (spec revision 15):** `_executingHash` (a transient hash of the executing calldata; `_scheduledCall` compares `keccak256(msg.data)`, Task 7); each item's `readyBlock` with a per-contract `SECONDS_PER_BLOCK` (`Params.secondsPerBlock`: vault 12, front door 2), so a halted chain cannot consume the veto; `pendingSince`, making `acceptOwnership` the transfer item's tail (within `EXECUTE_WINDOW`, from OPEN, no stamp since; `transferOwnership(0)` clears it); `setGuardian` also clears a guardian's bridge hold (the SG bound stays 15 days); the guardian may take over an owner-removed door (Removed to Unknown, its Reopen cancelled, the owner's launch-door hold made the guardian's; Task 10b); a scheduled `moveStake` clamped at execute; Task 8's `Actor` in `CascadeTypes`, `_stamp(Actor)` reverting on `None` and `holds(None)` false; no mint at an empty, underwater vault on round 2's rule (Task 10c); no inline assembly in any library, with the bytecode backstops, the whole `PayoutIn` unwritten by L3 and no value on a precompile call; Task 11's helper is `_requireScheduledIfLoosens`.

**2026-11-01, Phase 2's rulings (Tasks 5a to 5g, done; spec revision 14):** the unstake flag is the vault's transient `_unstaking`, set by the vault around its own L2 calls and never across a bridge call, and `Ledger` is `{pending, booked, ramping}`; L3 is `prepare`, `finish` and `cancel`, the vault orchestrates the walk between them, and L3 links only `CascadePayoutMath`; `PayoutIn` and `BatchIn` are as built (Tasks 5e and 5g); the library checker works on solc's resolved AST, with a sixth build check for a warning-free `src/`; ops reads v3-launch from `ops/builds/preaudit`; `[profile.parity]` uses `code_size_limit`; gate A2 measured the vault at 15,381 B, L1 3,286 B, L2 1,367 B, L3 4,500 B, `CascadePayoutMath` 1,867 B, the front door 14,349 B, the vault lens 5,130 B and the door lens 1,553 B.

- An item killed by a later stamp at `execute`, and `schedule`'s same-second refusal, have no named error in the spec; both revert `ExitsNotOpen()` (Task 8).
- `AlreadyActive` is listed as a vault error but the bridge activation needs it too; since revision 12 every error is declared once at file level, so it lives in `CascadeErrors.sol` with the rest (Tasks 5a, 7).
- OpenZeppelin's `Ownable2Step` keeps `_pendingOwner` private, so a scheduled `transferOwnership` cannot call it through a self-call; `CascadeBase` overrides `_checkOwner()` to admit the scheduled self-call, which makes OZ's `onlyOwner` the spec's `onlyOwnerOrScheduled` and keeps the `Ownable2Step` ABI (Task 7).
- `ExitsClosed(address by, bytes4 instrument)` and `ExitsReopened(bytes4 instrument)`, and `BatchParked`'s `reason` as a 4-byte selector, are this plan's choice of types (Tasks 8, 25).
- `deliverParked`'s call carries the same `PARK_GAS_RESERVE` cap as `_deliver`; `dropParked` of a non-empty park reverts `NotParked`; the staker's floor reverts a new `BelowOracleFloor` (Tasks 26, 27, 33).
- `redeemDirect` pays `_sub0(out, unmet)` floored to rao (Task 19).
- The code read-back fills each immutable by AST id, mapped to its variable through the AST, which needs `ast = true` in `foundry.toml` (no effect on bytecode) (Tasks 2, 45).
- **The libraries are created before Phase 3, not inside the tasks that change their subsystems** (Tasks 5e to 5g). Each is a behaviour-preserving move of today's v3.1 code, proven by the unchanged suite, and the v3.2 features are then written into it (Tasks 17 and 18 into L1, 19 and 20 into L2, 21 and 22 into L3). Creating them at Tasks 17 to 22 instead would leave Phase 3's 3.9 KB and Tasks 12 to 16 on a vault without the libraries' 4.3 KB of relief, which by §8's measurements crosses the 23,076 B gate, and probably EIP-170, around Tasks 12 to 14.
- The library interfaces' field lists (`BatchIn`, `PayoutIn`, `WalkParams`, `Ledger`) and function signatures are this plan's; §8.1 fixes only what each library writes and calls. L1 returns the queued batch for the vault to store (§8.1 lists L1's writes as balances, supply, origins and the windows, not the queue).
- The door lens reads the front door's `keeper` by `extsload` while the front door keeps its own public `keeper()` getter: revision 13 lists `keeper` among the door lens's deploy checks, but §8.1 moves only `CascadeBase`'s getters off the front door.
- "The code-size limit lifted in the test profile only" (§9.2) is `[profile.parity]` with `code_size_limit = 4294967295` (Foundry 1.7 has no `disable_code_size_limit` key) and the compiler settings of `[profile.default]`, so the bytecode is identical; the invariant campaigns run under it.
- The published vault ABI is generated into `contracts/abi/CascadeVault.json` and committed, so ops, the indexer and the web read one file and the build check catches a stale one.
- The monitor's "stage above founder" reads the web's `"early"` as the founder level, and the web gains a `"retired"` stage (Tasks 55, 60).
- §7 step 4's "0.01 TAO batch" was below the 0.04 TAO launch minimum deposit (and the 0.03 TAO floor); Task 38's docs pass corrected the spec to 0.04 TAO, which Task 67 sends.
