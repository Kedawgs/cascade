# Cross-chain rails for a Bittensor-resident vault (CCIP / Hyperlane / LayerZero / others) — v2 vault design

Scope: how a contract on Bittensor EVM (chain id 964) can send and receive "tokens + data" messages with Base and other user chains, what is delivered, what it costs, and what constrains it. Current as of 2026-10-21. Anything older is labelled.

Verification method used for the on-chain facts below: `eth_call` reads on 2026-10-21 against Bittensor EVM (`https://lite.chain.opentensor.ai`, cross-checked on `https://bittensor-finney.api.onfinality.io/public`) and Base (`https://mainnet.base.org`), using viem. Each such finding links the contract on the explorer ([evm.taostats.io](https://evm.taostats.io) / [basescan.org](https://basescan.org)); "read 2026-10-21" marks these. Fee quotes are `Router.getFee` return values, i.e. exactly what the router would charge at that moment. USD conversions use CoinGecko spot on 2026-10-21: TAO $270.70, ETH $2,441.53, LINK $12.32 — [CoinGecko simple price](https://api.coingecko.com/api/v3/simple/price?ids=bittensor,ethereum,chainlink&vs_currencies=usd).

Big picture in one paragraph: CCIP is the only rail that today moves TAO value between Bittensor EVM and Base, and it supports tokens + data in one atomically-executed message in both directions. But the "TAO" CCIP delivers on Bittensor EVM is **ForeverMoney's own mintable ERC-20** (`0xC5b6…0256`), released from a LockRelease pool — it is **not native TAO and not the canonical WETH9-style WTAO** (`0x5F3B…3522`). Getting native TAO to stake therefore means either redeeming through ForeverMoney's vault/gateway contracts (unverified source, no public API) or issuing Cascade's own CCIP token (CCT) wrapping canonical WTAO, which makes Cascade a bridge-token issuer. The Bittensor lanes have just been upgraded to CCIP 2.0 OnRamps/OffRamps (the 1.6 OffRamps are still registered), with per-message caps of 1 token, 32,000 bytes of data and an effective receiver gas budget of about 7.2M on Base→Bittensor (15M config on Bittensor→Base), a pool rate limit of 5,000 TAO per message with 0.6 TAO/s refill, and a cost of roughly $5–11 per Base→Bittensor batch message and $0.2–0.5 per Bittensor→Base message. Hyperlane core is live with a 3-of-5 / 3-of-4 default validator set, but has no TAO warp route (only USDC) and no stock way to deliver native value and data atomically; LayerZero v2 has an endpoint and six DVNs but no tokens; Wormhole and Axelar do not list chain 964.

## Key question 1 — CCIP on Bittensor EVM: addresses, lanes, programmable token transfers, what "TAO" is, pool types, unwrapping, Base side, third-party use, rate limits

### Takeaway
CCIP is live on Bittensor EVM (router `0xD941…60B8`, selector `2135107236357186872`) with lanes to Base, Ethereum, BNB Chain, Robinhood Chain and Solana (not Polygon). Programmable token transfers (one token + up to 32,000 bytes of data, delivered via `ccipReceive`) work in both directions. The only "TAO" registered with CCIP on Bittensor EVM is ForeverMoney's ERC-20 `0xC5b6…0256`, locked in a `LockReleaseTokenPool 1.5.1` and minted on Base as `0xf308…3d67` via a `BurnMintTokenPool 1.5.1`; the pools, token admin and rate limits are controlled by a 2-of-3 Safe (`0xADF6…3546`) that ForeverMoney operates. Any contract can use the router with this token (no sender allowlist), subject to a 5,000-TAO bucket per direction that refills at 0.6 TAO/s. The canonical WTAO (`0x5F3B…3522`, verified WETH9 fork with `deposit`/`withdraw`) is the CCIP fee token but has **no CCIP pool** and cannot be self-registered because it has no `owner()`/`getCCIPAdmin()`.

### Inferences
- For the v2 design, "bridged TAO" on the Bittensor side is an ERC-20 claim issued by ForeverMoney, not value the vault can stake directly. The adapter would have to (a) redeem FM-TAO for native TAO through ForeverMoney's contracts (the receipt above shows their own receiver burning FM-TAO into the AlphaVault on arrival), or (b) Cascade issues its own CCT: wrap native TAO into canonical WTAO (`deposit()`), lock it in a Cascade-owned LockRelease pool on Bittensor, mint a Cascade token on Base — then `ccipReceive` can `withdraw()` to native TAO atomically. Option (b) is clean technically but makes Cascade a bridge-token issuer (pool owner, rate-limit admin, liquidity/rebalancing), which the earlier notes flagged as a large operational burden; option (a) depends on an unverified third-party contract with no published integration API.
- Because WTAO has no `owner()`/`getCCIPAdmin()`, Cascade cannot self-register it; it would need a Cascade-deployed wrapper token (WETH9 clone with `getCCIPAdmin`) or manual registration by Chainlink.
- The 5,000-TAO capacity means any single `PAYOUTS` or `BATCH` message above 5,000 TAO (~$1.35M) fails at the pool; the 0.6 TAO/s refill caps sustained flow at ~51,840 TAO/day per direction. Batches should be capped at the bucket (or split) and the keeper should check `getCurrentInboundRateLimiterState` on the destination pool before sending.
- The same 2-of-3 Safe (ForeverMoney) can change rate limits, swap pools or set the pool to zero (which removes the token from CCIP) on both chains; Cascade inherits that governance risk if it uses FM-TAO.

### Gaps
- ForeverMoney's receiver/gateway/AlphaVault contracts are not source-verified on the explorer, so the exact redeem interface (and whether a third-party contract may call it) is unknown; ForeverMoney's docs describe only SDK/app integration ("applications should read the canonical deployment from the SDK").
- Rubicon's xSN pools' rate limits and whether their 1.6.1 pools accept programmable transfers were not probed.
- The Solana lane is enabled at the router but was not examined further (SVM payload limit is 640 bytes per Chainlink's SVM service-limits page, which would not fit a 100-entry batch) — [CCIP service limits (SVM)](https://docs.chain.link/ccip/service-limits/svm).

## Key question 2 — Delivery semantics a receiving contract must handle (ordering, msg.value, gas limit, out-of-order execution, reverts/manual execution, fees, sender verification, Bittensor-specific caveats)

### Takeaway
Tokens are released/minted to the receiver first and `ccipReceive` is called in the same transaction; if `ccipReceive` reverts, the whole execution (including the token transfer) reverts and the message goes to `FAILURE`, where anyone can retry it with a gas override that may only increase. `ccipReceive` is not payable (`msg.value` is always 0), `msg.sender` is the Router, and the message exposes `sourceChainSelector` and the abi-encoded `sender`. On the Bittensor lanes the per-message data cap is 32,000 bytes, the receiver gas budget is capped by a per-destination total (8,000,000 for Bittensor, 15,000,000 for Base, inclusive of ~300k overhead and per-byte payload gas), out-of-order execution is deprecated in CCIP 2.0 (lanes are now 2.0 on the send side), fees are paid in native/wrapped native or LINK and are independent of the token amount, and the 1.6 OffRamps on these lanes have `isRMNVerificationDisabled = true` with a 1-hour permissionless-execution threshold.

### Cited Findings

Ordering, atomicity, token-only fallback (OffRamp 1.6.0 — the version registered on these lanes):
- In `executeSingleMessage`: `destTokenAmounts = _releaseOrMintTokens(` is called first (when the message carries tokens); the receiver is **not** called if `(message.data.length == 0 && message.gasLimit == 0) || message.receiver.code.length == 0 || !message.receiver._supportsInterfaceReverting(type(IAny2EVMMessageReceiver).interfaceId)`; otherwise the Router is called via `.routeMessage(any2EvmMessage, i_gasForCallExactCheck, message.gasLimit, message.receiver)` and `if (!success) revert ReceiverError(returnData);` — [OffRamp.sol v1.6.0](https://raw.githubusercontent.com/smartcontractkit/chainlink-ccip/contracts-ccip-v1.6.0/chains/evm/contracts/offRamp/OffRamp.sol).
- Receiver API: `function ccipReceive(Client.Any2EVMMessage calldata message) external virtual override onlyRouter;` "If this function reverts, any associated token transfers also revert"; "Failed messages enter a FAILED state and become available for manual execution"; `supportsInterface`: "If returns true: tokens are transferred and ccipReceive is called atomically. If returns false or reverts: only tokens are transferred"; no code → only tokens — [CCIPReceiver v1.6.1 API](https://docs.chain.link/ccip/api-reference/evm/v1.6.1/ccip-receiver.md); same statements in the [v2.0.0 CCIPReceiver API](https://docs.chain.link/ccip/evm/api-reference/v2.0.0/ccip-receiver) ("If `_ccipReceive` reverts, message execution fails and any associated token transfers also revert").

### Inferences
- The v2 `ICascadeReceiver.onBridgeMessage(... amount) payable` native-value path does not map onto CCIP: value arrives as an ERC-20 (FM-TAO or a Cascade CCT) to the adapter before `ccipReceive`; the adapter must convert (redeem/`withdraw`) and then call the vault with `msg.value == amount`. The vault's `msg.value != amount → ValueMismatch` check still works if the adapter does the conversion in the same transaction.
- A revert inside `ccipReceive` (e.g. a precompile "too early" or a bug) is safe for funds: nothing is delivered, the message sits in `FAILURE`, and anyone (the keeper) can retry with more gas. The design's `DuplicateBatch` replay guard remains necessary because retries re-deliver the same `messageId` only after a failure, but a second *successful* execution is impossible (`SkippedAlreadyExecutedMessage`).
- Because `gasLimit` is priced and non-refundable, and the cap is a *total* (user gas + 300k + 90k + 20 gas/byte on Bittensor), the practical ceiling for a 7 KB batch into Bittensor is ~7.2–7.4M user gas; for data-only messages ~7.5M.

### Gaps
- Exact CCIP 2.0 `FeeQuoter` struct field names for the minor words (the 32,000 / 8,000,000 / 15,000,000 values are unambiguous; "20 vs 100 gas per byte" and "90,000/200,000" are inferred from position).
- The 2.0 executor's retry window length is not published.
- Whether the Chainlink executor will keep auto-executing messages that exceed some internal gas threshold on Bittensor (no documented cap beyond the FeeQuoter config).

## Key question 3 — Gas on delivery: can one `ccipReceive` on Bittensor EVM afford 100 ERC-20 mints plus staking precompile calls?

### Takeaway
Yes, with headroom but not by a wide margin: the Base→Bittensor lane lets the sender buy up to ~7.2M receiver gas (config cap 8M total), the Bittensor block limit is 75M, and the cost of a 7 KB message at 5–7M gas is $7.7–10.4 per batch. A 100-entry batch of fresh-address mints plus two or three precompile calls plausibly needs 3–4.5M gas, so it fits in a single 2.0 message but exceeds the 3M ceiling that applied to V1 lanes and that Chainlink still documents for V1.

### Cited Findings

- Price of that gas: Base→Bittensor quotes of 0.0031600 ETH at 5M, 0.0037143 ETH at 6M, 0.0042646 ETH at 7M, 0.0043779 ETH at 7.2M (read 2026-10-21) — [Base router](https://basescan.org/address/0x881e3A65B4d4a04dD529061dd0071cf975F58bCD). ### Inferences
- Rough budget (not measured): an OpenZeppelin `_mint` to a cold, previously-empty address is ~20k (new balance slot) + ~2.9k (`totalSupply`, warm after the first) + ~1.8k (Transfer event) + loop/decode overhead ≈ 25–30k, so 100 entries ≈ 2.5–3M; add calldata/`abi.decode` of 7 KB, one `claimRootWithHotkey` and one `addStake` precompile call (precompile gas on Bittensor is not published), the price computation and events — a total around 3.5–4.5M is plausible. That exceeds V1's 3M but fits under the 2.0 cap of ~7.2M with 2–3M of headroom.
- Chainlink's own advice argues for the lighter pattern: record the batch in `ccipReceive` (mint shares, queue payouts) and let `_stakeIdle()` / unstaking happen in a separate permissionless call, which also removes the risk that a precompile revert turns a whole batch into a `FAILURE` needing manual retry.
- `MAX_ENTRIES = 100` should be fixed only after Foundry gas measurements on a fork of Bittensor EVM; if the measured total approaches ~6M, lower the cap (e.g. 50–60 entries) or split batches.

### Gaps
- No published gas costs for the Bittensor staking precompiles (`0x805`); must be measured on a fork.
- Whether Chainlink will raise `maxPerMsgGasLimit` for Bittensor on request is undocumented.

"When first deploying with the CLI, new HWR use a Trusted Relayer ISM out of the box so you don't need to run a relayer or validator"; that ISM means "the `relayer` can execute arbitrary messages on the HWR"; "Removing the Trusted Relayer ISM is a crucial step when preparing your HWR for production" — [Hyperlane: remove trusted relayer](https://docs.hyperlane.xyz/docs/guides/production/warp-route-deployment/remove-trusted-relayer.md).

### Inferences
- Hyperlane can carry the *data* half of Cascade's messages today, secured by Abacus Works' default 3-of-5 / 3-of-4 validator sets (which the vault can override with its own ISM). It cannot carry TAO *value* without Cascade deploying and owning a warp route; even then stock HypNative pays the recipient with `sendValue` and no data, so atomic "value + batch" needs a custom TokenRouter override (`_handle`) — a bridge-tier contract to audit and operate, plus the TrustedRelayerIsm removal and ISM hardening the Autheo case illustrates.
- A two-message pattern (HypNative value, Mailbox data) is non-atomic; the front door's `TokensNotReceived` guard in the v2 spec exists precisely for such adapters, but it forces a re-delivery dance and keeper logic.
- The #8589 claim is unverified and was closed without comment; it is a yellow flag for HypERC20Collateral/HypNative, not evidence of a bug.

## Key question 6 — Which user chains reach Bittensor directly today, and the realistic path for chains without a lane

### Takeaway
CCIP lanes exist from Bittensor EVM to Base, Ethereum, BNB Chain, Robinhood Chain and Solana; Polygon is not a CCIP destination from Bittensor. But the ForeverMoney TAO token is only configured for Base and Robinhood (Ethereum/BNB pools disabled), so Base is the only user chain where "bridged TAO" exists with liquidity. Chains without a lane (and Ethereum/BNB/Polygon for TAO value) should be served by hopping to Base inside the app.

### Cited Findings
- `Router.isChainSupported` on Bittensor: Base, Ethereum, BNB, Robinhood, Solana true; Polygon false; the 1.6 OffRamp on Bittensor has enabled source configs for Base, Ethereum and BNB (read 2026-10-21) — [Bittensor router](https://evm.taostats.io/address/0xD941fBEcD2b971d0F54b4C34286C95faB52B60B8); [Bittensor OffRamp 1.6](https://evm.taostats.io/address/0x51a6150400ed9F0Ae240F5D1b15E3b45Fc4339C7).

## Key question 7 — Existing contracts on Bittensor EVM that already receive CCIP/Hyperlane messages with data

### Takeaway
ForeverMoney's receiver contracts are the only live example found of a Bittensor-EVM contract that receives CCIP tokens + data and acts on them (burning the bridged token into their vault in the same transaction); the "alpha gateway" implements the CCIP receiver interface and calls the staking/balance precompiles, but none of these contracts is source-verified, so the exact code is unavailable. Rubicon's xSN pools show only token-only transfers. TaoFi's Hyperlane ICA pattern (from earlier research) is the only Hyperlane data-receiving precedent, and TaoFi is no longer a viable dependency.

### Cited Findings
